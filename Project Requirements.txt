1. Society & Building Structure
Q1. Will the application support one society or multiple societies?

Answer: Multiple societies.

The database will be designed to support:

Society
   |
   +--- Wing
          |
          +--- Flat

Even if the first deployment contains only one society, the database will support multiple societies.

Q2. Do we need a Floor entity?

Answer: No, not in V1.

We will use the flat number to identify the floor logically.

Example:

101 → Floor 1
201 → Floor 2
301 → Floor 3
...
701 → Floor 7

The application should not depend on this pattern programmatically. Flat numbers are identifiers, not a replacement for a Floor entity.

Q3. How will flats be numbered?

Answer: Flat numbers will be manually entered.

Example:

101
102
103
104
105


201
202
203
204
205

The system will not automatically generate flat numbers.

Q4. Are the number of floors/flats fixed?

Answer: The current society structure is known, but the application should not hard-code 35 flats or 7 floors.

Individual flats can be added or deleted.

Q5. Are multiple wings/buildings supported?

Answer: Yes.

Recommended naming:

Wing A
Wing B
Wing C

For the database, we should store a configurable wingName rather than hard-coding A/B/C.

2. Flat
Q6. What area should be used for maintenance?

Answer: Built-up area.

Q7. Can flat area change after creation?

Answer: No in V1.

The built-up area is considered fixed.

Q8. What data type should be used for sqft?

Answer: BigDecimal.

Example:

private BigDecimal flatSqft;
Q9. Can one Member own multiple Flats?

Answer: Yes.

This is an important design rule.

Example:

Suresh
  |
  +--- Flat 101
  |
  +--- Flat 205

There should be one Member record, not two.

Q10. Can multiple Members jointly own one Flat?

Answer: No.

One Flat has one current owner in V1.

Q11. Can a company own a Flat?

Answer: No.

Only an individual Member can own a Flat in V1.

Q12. Can ownership be transferred?

Answer: Yes.

Example:

Flat 101
Owner → Suresh


Suresh sells Flat 101


Flat 101
Owner → Ravi
Q13. Do we need ownership history?

Answer: Not as a separate entity in V1.

However, ownership changes should be auditable.

A future V2 entity can be:

FlatOwnershipHistory
Q14. Can a Flat exist without an owner?

Answer: No.

A Flat should always have a current owner.

Q15. Do we need Flat Status?

Answer: No.

We are removing:

VACANT
OWNER_OCCUPIED
TENANT_OCCUPIED
COMPANY_LEASED

from V1.

If required later, we can introduce it.

Q16. Do we need tenant management?

Answer: No, not in V1.

Q17. Should the owner's name be displayed?

Answer: Yes.

Whenever Flat information is returned, the owner's name should be available where appropriate.

If the Member no longer owns any Flat and has no active society relationship:

6. Maintenance Rate
Q43. What is the initial maintenance rate?

Answer:

₹3 per sqft per month
Q44. Does the rate apply to all Flats?

Answer: Yes.

Q45. Can the rate change?

Answer: Yes.

Q46. Who can change the rate?

Answer: Admin.

Q47. Should rate changes be authorized/audited?

Answer: Yes.

Q48. Should rate history be maintained?

Answer: Yes.

Example:

Apr 2026 → ₹3.00
May 2026 → ₹3.00
Jan 2027 → ₹3.50
Q49. Should old bills change when the rate changes?

Answer: No.

Historical bills must retain the original rate.

Q50. Should the rate be hard-coded?

Answer: No.

It should be configurable.

7. Maintenance Calculation
Q51. What is the maintenance formula?

Answer:

Maintenance = Built-up Area × Maintenance Rate

Example:

650 sqft × ₹3
= ₹1,950
Q52. What datatype should monetary values use?

Answer: BigDecimal.

8. Monthly Maintenance Bill
Q53. When should monthly bills be generated?

Answer: 1st of every month.

Q54. Should generation be automatic?

Answer: Yes.

A scheduled job will generate the bills automatically.

Q55. Should Admin have a manual generation/retry option?

Answer: Yes.

This is a safety mechanism in case the scheduled job fails.

Q56. Can duplicate bills be generated?

Answer: No.

The following combination must be unique:

Flat + Month + Year

Q59. Should the maintenance rate used for billing be stored?

Answer: Yes.

This creates a historical snapshot.
